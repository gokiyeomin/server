# REFERENCE

## 목적

이 문서는 최소 품질 기준을 정의한다.

문서의 완성도, 전문성, 설득력, 콘텐츠 전략은 보지 않는다.

이 기준의 목적은 다음과 같다.

- 문서 목적이 명확하게 표현되었는지 확인한다.
- 대상 독자가 식별 가능한지 확인한다.
- 용어 사용이 일관적인지 확인한다.
- 문서 구조가 존재하는지 확인한다.
- 기본적인 형식 요건을 충족하는지 확인한다.

## 범위

이 기준은 다음 문서 유형에 적용할 수 있다.

- 기술 블로그
- 엔지니어링 문서
- 프로젝트 회고
- 기술 도입 사례
- 운영 경험 공유
- 개발 관련 가이드 문서

## 점검 원칙

이 문서는 최소 품질 기준만을 점검한다.

다음 항목은 점검 대상에 포함하지 않는다.

- 글의 우수성
- 기술적 난이도
- 논리 전개의 설득력
- 콘텐츠 전략 적합성
- 작성자의 전문성
- 개인적 문체 선호
- 마케팅 효과
- 검색 유입 가능성

## 결과 분류

P0 항목은 반드시 고쳐야 통과한다. P1과 P2는 고치지 않고 공개했을 때 독자가 받는 영향이 어느 정도인지 나타내며, 고칠지는 작성자가 정한다.

### P0(필수 수정)

외부 공개 전에 반드시 고쳐야 하는 항목. 통과하려면 수정이 필요하다.

P0는 문서가 무엇을 다루는지, 누구를 위한 것인지 식별할 수 없는 근본 결함, 제목이 아예 없는 경우, 사내 경로나 개인정보 같은 민감 정보가 노출된 경우, API 키나 토큰 같은 인증 정보가 노출된 경우, 인용문이나 외부에서 가져온 자료, 통계, 이미지에 출처가 없는 경우, 오탈자나 명백한 맞춤법 오류가 있는 경우, 작성 중 흔적이 그대로 남은 경우에 부여한다.

### P1(권장 수정)

최소 품질 기준은 충족하지만 독자의 이해를 방해한다. 공개는 가능하나 독자가 내용을 파악하기 어려우므로 수정을 권장한다.

### P2(선택 수정)

독자가 이해하는 데에 문제는 없으나 문서 품질을 향상하는 데 고려할 항목.

## 점검 항목

이 기준은 18개 항목을 점검한다. 항목은 두 부로 나뉜다.

- **1부(구조와 틀)**: 글 전체를 읽어야 판정되는 항목. 이 글이 무엇을, 누구에게, 어떤 골격으로 말하는지를 본다.
- **2부(표현과 세부)**: 걸린 위치만 보면 판정되는 항목. 문장, 단어, 형식, 자료가 괜찮은지를 본다.

1부와 2부는 나누어 보되, 통과 판정은 부와 무관하다. 어느 부에서든 P0가 하나라도 있으면 통과를 막는다.

### 1부: 구조와 틀

1. 문서 목적
2. 대상 독자
3. 제목 명확성
4. 문서 구조

### 2부: 표현과 세부

5. 민감 정보
6. 용어 약어 풀이
7. 용어 일관성
8. 번역 투
9. 겹말(중복 표현)
10. 형식 일관성
11. 코드 표현 형식
12. 링크 무결성
13. 맞춤법 및 외래어 표기
14. 출처 표기
15. 저작권
16. 비문(주술 호응)
17. 인증/시크릿 정보 노출
18. 미완성 흔적 잔존

## 판정 원칙

- 통과 여부가 애매하면 통과로 본다. 다만 항목별 결과 분류에 불확실하거나 애매한 경우의 등급이 따로 정해져 있으면 그 등급을 따른다. 이 기준은 최소선만 확인한다. 단 이 "애매하면 통과"는 항목의 통과/실패 판정에만 적용한다. 항목이 통과하더라도 본문에 눈에 띄는 개선점이 있으면 결과 구성 7번 통과 항목 문단에 개선 제안으로 적는다. 보완 항목에 🔵 P2 헤딩을 달지 않고, 점검표 판정과 건수는 통과로 둔다.
- 한 항목에서 여러 위치가 걸리면 뭉쳐서 줄이지 말고, 보완 항목에 위치별로 각각 적는다. 여러 곳이 같은 원칙에 걸리더라도 줄여 묶지 않는다. 다만 건수는 항목 단위로 센다(결과 구성 3번).
- P0는 통과를 막는 등급이다. 어떤 경우에 P0를 부여하는지는 위 "결과 분류"의 P0 정의를 따른다. P0는 1부와 2부 어디에 있든 통과를 막는다.
- 나머지 항목은 실패해도 통과에는 지장이 없다. 개선이 필요하면 P1, 선택이면 P2로 둔다. 한 항목 안에서 등급이 갈릴 수도 있다. 예를 들어 13번은 오탈자를 P0로, 띄어쓰기나 외래어 표기를 P2로 둔다. 이때 그 항목이 실패로 잡히더라도 P0가 아닌 한 통과를 막지 않는다.
- 확인 대상이 아닌 것은 지적하지 않는다. 무엇을 보지 않는지는 위 "점검 원칙"을 따른다.

## 항목별 세부 기준

### 1부: 구조와 틀

#### 1. 문서 목적

**점검 대상**: 문서가 전달하려는 주제 또는 목표가 식별 가능한지 확인한다.

**통과 조건**
- 문서의 주제 또는 목표가 명시되어 있다.
- 문서 초반부에서 독자가 문서의 범위를 이해할 수 있다.

**실패 조건**
- 문서가 무엇을 설명하려는지 식별하기 어렵다.

**결과 분류**: 실패 시 P0

#### 2. 대상 독자

**점검 대상**: 문서가 어떤 독자를 대상으로 작성되었는지 식별 가능한지 확인한다.

**통과 조건**
- 대상 독자가 명시되어 있다.
- 또는 문맥상 대상 독자가 명확하게 식별된다.

**실패 조건**
- 대상 독자를 식별하기 어렵다.

**결과 분류**: 실패 시 P0. 독자는 식별되지만 요구되는 선행 지식이 적혀 있지 않으면 통과로 두고 통과 항목 문단에 개선 제안으로 적는다.

#### 3. 제목 명확성

**점검 대상**: 제목이 문서의 내용을 가리키는지 확인한다. 제목이 매력적인지, 검색에 유리한지는 보지 않는다.

**통과 조건**
- 제목이 존재한다.
- 제목과 본문 내용이 크게 어긋나지 않는다.

**실패 조건**
- 제목이 없다.
- 제목이 본문 내용과 무관하거나 오해를 유발한다.
- 제목만으로 문서가 다루는 대상을 전혀 짐작할 수 없다.

**결과 분류**
- 제목이 아예 없는 경우: P0
- 제목이 있으나 내용과 어긋나 독자를 오도하는 경우: P1
- 제목이 내용을 가리키기는 하나 모호하거나 다듬을 여지가 있는 경우: P2

#### 4. 문서 구조

**점검 대상**: 문서에 내용을 탐색할 수 있는 구조가 존재하는지 확인한다. 구조가 최적인지, 흐름이 매끄러운지는 보지 않는다.

**통과 조건**
- 제목, 단락, 또는 섹션 구분이 존재해 내용을 나누어 읽을 수 있다.
- 분량이 긴 문서에 최소한의 단락 구분이 있다.

**실패 조건**
- 구분 없는 하나의 덩어리로 작성되어 내용 탐색이 어렵다.
- 섹션 구분이 내용과 무관하게 임의로 나뉘어 구조 역할을 못 한다.

**결과 분류**
- 구조가 사실상 없어 긴 본문을 탐색하기 어려운 경우: P1
- 구조는 있으나 일부 섹션이 과도하게 길거나 구분이 거친 경우: P2

### 2부: 표현과 세부

#### 5. 민감 정보

**점검 대상**: 외부에 공개하면 안 되는 정보가 본문이나 이미지에 노출되었는지 확인한다.

**통과 조건**
- 사내 전용 정보(내부 경로, 서버 주소, 비공개 시스템명), 개인 식별 정보, 동의 없는 인물 사진, 비공개 수치가 노출되지 않는다.

**실패 조건**
- 사내 경로나 내부 주소가 본문이나 캡처 이미지에 그대로 드러난다.
- 개인을 식별할 수 있는 정보나 사진, 공개되면 안 되는 수치가 포함된다.

**결과 분류**
- 민감 정보 노출이 명백한 경우: P0
- 노출 여부가 불확실하거나 경미한 경우: P1

#### 6. 용어 약어 풀이

**점검 대상**: 용어나 약어가 처음 등장할 때 풀이가 붙어 있는지 확인한다. 용어 선택이 적절한지, 표준 용어인지는 보지 않는다.

**통과 조건**
- 약어를 쓰는 경우 처음 등장할 때 풀어 쓰거나 문맥으로 의미가 통한다.
- LLM, GPT, API, OS, AWS처럼 해당 분야에서 널리 쓰이는 약어는 풀이가 없어도 무방하다.

**실패 조건**
- 약어나 줄임말이 풀이 없이 쓰여 의미를 추정해야 한다.

**결과 분류**
- 처음 나오는 약어에 풀이가 없어 독자가 막히는 경우: P1
- 부수적 약어 하나가 풀이 없이 쓰인 정도인 경우: P2

약어는 처음 등장할 때 풀어 쓴다(예: PoC → PoC(Proof of Concept, 개념 검증)).

#### 7. 용어 일관성

**점검 대상**: 같은 대상을 가리키는 용어가 문서 안에서 하나로 통일되어 쓰였는지 확인한다. 용어 선택이 적절한지, 표준 용어인지는 보지 않는다.

**통과 조건**
- 하나의 대상을 하나의 용어로 일관되게 지칭한다.

**실패 조건**
- 같은 대상을 여러 용어로 혼용해 독자가 같은 것인지 다른 것인지 판단하기 어렵다.

**결과 분류**
- 핵심 개념의 용어 혼용으로 내용 이해가 방해되는 경우: P1
- 부수적 용어의 표기가 흔들리는 정도(예: 띄어쓰기, 영문/한글 혼용)인 경우: P2

용어 혼용은 한쪽으로 통일한다(예: '다운로드한다'와 '내려받는다' 혼용 → '다운로드한다'로 통일).

#### 8. 번역 투

**점검 대상**: 번역 투(자연스러운 우리말 대신 쓰인 표현), 특히 이중 피동이 쓰였는지 확인한다. 이중 피동처럼 분명한 것만 짚는다.

**통과 조건**
- 피동을 겹쳐 쓰지 않는다(이중 피동이 없다).

**실패 조건**
- "되어진다", "보여지다", "만들어지게 된다"처럼 피동이 겹쳐 쓰였다.

**결과 분류**
- 이중 피동이 쓰인 경우: P1
- 그 밖에 다듬으면 좋은 번역 투가 있는 경우: P2

이중 피동은 피동을 한 번만 쓴다(되어진다 → 된다).

#### 9. 겹말(중복 표현)

**점검 대상**: 같은 뜻을 두 번 겹쳐 쓴 표현이 있는지 확인한다. 의미가 분명히 겹치는 것만 짚는다.

**통과 조건**
- 같은 의미가 한 번만 표현된다.

**실패 조건**
- "미리 예약", "다시 재시작", "약 30% 정도"처럼 같은 뜻이 겹쳐 쓰였다.

**결과 분류**
- 의미가 분명히 겹친 경우: P1
- 겹말로 볼 수 있으나 굳어져 자연스러운 경우: P2

겹말은 겹친 부분을 뺀다(미리 예약 → 예약).

#### 10. 형식 일관성

**점검 대상**: 문서의 기본 형식이 깨지지 않고 일관되게 적용되었는지 확인한다. 디자인 완성도나 스타일 선호는 보지 않는다.

**통과 조건**
- 제목 단계(헤딩 레벨), 목록, 강조 등의 마크업이 깨지지 않고 적용된다.
- 같은 종류의 요소가 일관된 형식으로 표현된다.

**실패 조건**
- 마크업이 깨져 일부 내용이 의도와 다르게 렌더링된다.
- 헤딩 레벨이 뒤섞여 문서 위계를 파악하기 어렵다.

**결과 분류**
- 형식 깨짐으로 내용이 잘못 보이거나 위계 파악이 안 되는 경우: P1
- 형식이 일부 일관되지 않으나 읽는 데 지장은 없는 경우: P2

#### 11. 코드 표현 형식

**점검 대상**: 코드와 예시가 본문과 구분되어 식별 가능한 형식으로 표현되었는지 확인한다. 코드의 정확성이나 품질은 보지 않는다.

**통과 조건**
- 코드가 코드 블록이나 인라인 코드 형식으로 본문과 구분된다.
- 예시(명령어, 입출력, 설정 값 등)가 어디까지가 예시인지 식별 가능하다.

**실패 조건**
- 코드가 일반 본문에 섞여 코드인지 설명인지 구분되지 않는다.
- 코드 블록이 깨져 들여쓰기나 줄바꿈이 사라져 의미가 달라진다.

**결과 분류**
- 코드와 본문이 구분되지 않거나 블록이 깨져 코드 해석이 어려운 경우: P1
- 코드 식별은 되나 언어 표기 누락 등 형식이 덜 다듬어진 경우: P2

#### 12. 링크 무결성

**점검 대상**: 문서에 포함된 링크와 내부 참조가 유효한지 확인한다. 참조 출처의 권위나 인용의 충분함은 보지 않는다.

**통과 조건**
- 본문이 가리키는 링크와 참조가 의도한 대상으로 연결된다.
- 내부 참조(섹션, 그림, 표 번호 등)가 실제 대상과 일치한다.

**실패 조건**
- 링크가 깨졌거나 잘못된 대상으로 연결된다.
- 본문이 언급한 그림, 표, 섹션이 문서에 존재하지 않는다.

외부 URL은 실제로 접속해 보지 않는다. 대상이 있는 링크의 형식 오류와 문서 안 참조만 판정한다. 빈 링크(`[]()`)와 빈 이미지 링크(`![]()`)는 18번 미완성 흔적에서 P0로 판정하고 12번에서 다시 세지 않는다. 경로는 있으나 파일이 없는 로컬 이미지는 12번에서 판정한다. 링크와 참조가 하나도 없으면 12번은 통과다. 외부 링크가 있으면 목적 안내(`ℹ️`)에 발행본에서 링크를 직접 눌러 확인하라고 적는다.

**결과 분류**
- 내용 이해에 필요한 핵심 링크나 참조가 깨진 경우: P1
- 부수적 외부 링크 일부가 유효하지 않거나 표기가 불완전한 경우: P2

#### 13. 맞춤법 및 외래어 표기

**점검 대상**: 기본적인 맞춤법, 띄어쓰기, 문장 부호, 외래어 표기가 올바른지 확인한다. 문체나 표현을 다듬는 일은 보지 않는다. 판정 기준은 국립국어원 표준국어대사전, 한글 맞춤법, 외래어 표기법을 따른다.

**통과 조건**
- 오탈자나 명백한 맞춤법 오류가 없다.
- 조사나 접사의 띄어쓰기가 맞다.
- 한글 문장 부호를 올바르게 사용했다.
- 외래어 표기가 외래어 표기법에 맞다.

**실패 조건**
- 오탈자나 명백한 맞춤법 오류가 있다.
- 띄어쓰기나 문장 부호 오류가 있다.
- 외래어 표기가 표기법과 다르다.

**결과 분류**
- 오탈자, 명백한 맞춤법 오류: P0
- 띄어쓰기, 문장 부호 오류: P2(띄어쓰기 오류로 의미가 헷갈리면 P1)
- 외래어 표기 오류: P2(틀려도 통과를 막지 않는다)

맞춤법은 올바른 표기로 고친다(예: 안되 → 안 돼, 성능이 낳다 → 성능이 낫다).

#### 14. 출처 표기

**점검 대상**: 인용문이나 외부에서 가져온 자료, 통계, 이미지에 출처가 표기되어 있는지만 확인한다. 출처가 믿을 만한지(신뢰도)나 인용이 충분한지는 이 최소 점검에서 보지 않는다.

인용문이나 외부에서 가져온 자료, 통계, 이미지에는 출처를 반드시 표기해야 한다. 출처가 빠지면 P0로 둔다.

**통과 조건**
- 외부 자료에서 인용한 문장, 수치, 이미지에 출처(자료명, 링크, 기관명 등)가 있다.
- 본인 경험이나 자체 측정 데이터처럼 출처가 필요 없는 내용은 그대로 둔다.

**실패 조건**
- 외부에서 가져온 것으로 보이는 수치나 주장, 이미지에 출처가 없다.
- 인용한 자료의 출처를 독자가 찾을 수 없다.

**결과 분류**
- 외부 인용, 통계, 이미지의 출처가 빠진 경우: P0
- 자체 데이터와 외부 데이터의 경계가 불분명해 출처 필요 여부가 애매한 경우: P1

출처는 누락 시 반드시 채운다. 자료 종류별 표기 방식은 다음과 같다.

- 도서) 저자, 『책 제목』, 출판사, 출판 연도, 인용 쪽수
- 웹 문서) 글 제목, 사이트 이름, URL, 확인한 날짜
- AI 이미지) 생성에 사용한 도구 이름과 AI로 생성한 이미지임을 함께 표기

#### 15. 저작권

**점검 대상**: 사용한 이미지와 자료에 저작권 문제 소지가 없는지 확인한다. 출처가 믿을 만한지(신뢰도)는 보지 않는다.

**통과 조건**
- 직접 제작했거나 사용이 허락된 이미지를 쓴다.
- 인용한 자료에 저작권 문제 소지가 없다.

**실패 조건**
- 사용 허락이 불분명한 이미지나 출처 불명의 짤(밈)을 쓴다.

**결과 분류**
- 사용 허락이 불분명한 이미지나 짤을 사용한 경우: P1

#### 16. 비문(주술 호응)

**점검 대상**: 한 문장 안에서 주어와 서술어가 호응하지 않아 뜻이 통하지 않는 문장이 있는지 확인한다. 주술이 어긋나 의미가 막히는 분명한 경우만 짚는다.

**통과 조건**
- 한 문장 안에서 주어와 서술어가 호응한다.

**실패 조건**
- 주어와 서술어가 어긋나 문장의 뜻이 통하지 않는다.
- 문장이 길어지며 주어가 받을 서술어가 사라지거나 뒤바뀐다.

**결과 분류**
- 주술 호응이 어긋나 뜻이 막히는 경우: P1
- 호응이 다소 어색하나 뜻은 통하는 경우: P2

비문은 주어와 서술어가 맞물리게 고친다.

#### 17. 인증/시크릿 정보 노출

**점검 대상**: API 키, 토큰, 비밀번호, 커넥션 스트링, .env 값, Authorization 헤더 같은 인증 및 접속 정보가 본문이나 코드, 캡처 이미지에 노출되었는지 확인한다.

**통과 조건**
- 실제 인증 정보가 없거나, 예시용 값은 더미 값(YOUR_API_KEY, xxxx 등)으로 가렸다.

**실패 조건**
- 실제 API 키, 토큰, 비밀번호, 커넥션 스트링, .env 값이 본문이나 코드 블록, 캡처 이미지에 그대로 드러난다.

**결과 분류**
- 인증 정보 노출이 명백한 경우: P0
- 더미 값인지 실제 값인지 불확실한 경우: P1

5번 민감 정보가 내부 경로와 개인정보를 본다면, 이 항목은 인증 및 접속 정보를 따로 본다.

#### 18. 미완성 흔적 잔존

**점검 대상**: 공개본에 작성 중 흔적(TODO, 작성 메모, 플레이스홀더, 빈 이미지 링크, 빈 링크, 중간에 끊긴 문장)이 남았는지 확인한다.

**통과 조건**
- "여기 수정", "내용 추가 예정", "작성 중", "(이미지 첨부)", 빈 `![]()`, 빈 `[]()`, 쓰다 만 문장이 없다.
- 주제어로 쓰인 "TODO"처럼 의도한 표현은 흔적으로 보지 않는다.

**실패 조건**
- 작성 중 메모나 플레이스홀더, 빈 이미지 링크(`![]()`)나 빈 링크(`[]()`)가 남아 있다.
- 서술어 없이 조사나 접속사로 끊겨 끝난 문장이 있다(예: "이 문제는 다음과 같은 방법으로").

**결과 분류**: 실패 시 P0

미완성 흔적은 공개 전에 반드시 지운다.

## 출력 형식

결과는 마크다운으로 채팅에 바로 출력한다. 파일로는 저장하지 않는다. 입력이 저장소 안의 파일이면 결과 파일이 원고와 함께 커밋될 수 있기 때문이다.

사용자가 파일 저장을 요청하면 그때 저장한다. 파일명은 `<원본 파일명에서 확장자를 뺀 이름>_점검.md`로 한다. 같은 원본을 다시 점검해 이 파일이 이미 있으면 덮어쓰지 않고 `_점검_v2.md`, `_점검_v3.md`처럼 번호를 올려 새로 저장한다(첫 점검은 번호를 붙이지 않는다). 저장 위치는 입력이 파일이면 원본과 같은 폴더, 붙여 넣은 본문이면 현재 작업 폴더(cwd)다. 붙여 넣은 본문이라 원본 파일명이 없으면 `기술문서_점검.md`로 저장한다.

요청을 받아 저장한 뒤에는 저장 경로를 클릭 가능한 `file:///` 링크로 한 줄 안내한다. 링크에 보이는 텍스트는 한글 경로가 그대로 읽히도록 적고, 퍼센트 인코딩된(`%ED%95...`) 경로는 노출하지 않는다.

### 출력 어조

점검 결과로 출력하는 모든 서술 문장은 '합니다'체로 통일한다. 판정 설명, 목적 안내(ℹ️), 보완 항목의 규칙 문장과 위치 서술, 확인 불가 설명, 통과 항목, 푸터까지 한 어조로 쓴다. "확인됐다", "통과한다", "아니다" 같은 평서체나 반말을 섞지 않는다(예: "오탈자가 확인됐다" → "오탈자가 확인되었습니다", "글을 더 좋게 만드는 도구가 아니다" → "글을 더 좋게 만드는 도구가 아닙니다").

### 결과 구성

결과는 다음 순서로 구성한다.

1. **제목과 판정**: `# 📋 최소 품질 점검 결과`로 시작한다. 바로 아래 인용 블록(`>`)에 세 단락을 각각 빈 인용 줄(`>`)로 나눠 적는다.
   - 1단락: `ℹ️ `로 시작하는 점검 안내 한 줄. 외부 공개 전 최소 품질만 보는 자가 점검이며 글의 우수성은 평가하지 않는다는 내용.
   - 2단락: `등급:`으로 시작하는 등급 안내 한 줄. P0는 공개 전 반드시 고쳐야 하는 항목, P1은 이해를 방해해 수정을 권하는 항목, P2는 이해에는 문제가 없으나 품질을 높이는 선택 항목.
   - 3단락: 판정 상태 이모지로 시작하는 판정 한 줄과 짧은 설명. P0가 0건이면 `✅ 판정: 통과`, 1건 이상이면 `⚠️ 판정: 보완 필요(P0 n건)`.
2. **점검 정보 표**: 점검 대상 문서, 점검일(`월. 일.(요일)` 형식), 점검 기준(`최소 품질 점검 / 18개 항목`)을 2열 표로 적는다.
3. **등급 요약 줄**: `🔴 P0 n, 🟡 P1 n, 🔵 P2 n, ✅ 통과 n, ➖ 확인 불가 n` 형식으로 굵게 적는다. 통과 비율은 확인 불가를 뺀 점검 가능 항목 수를 분모로 적는다(예: `✅ 통과 12 / 15`). 확인 불가가 없으면 분모는 18이다. 판정 줄의 `P0 n건`과 요약 줄의 숫자는 모두 항목 단위로 센다. 한 항목은 점검표의 판정 하나로만 세므로 요약 줄 숫자의 합은 늘 18이다. 한 항목에서 여러 곳이 걸려도 1건이고, 걸린 위치는 6번 보완 항목에 모두 적는다. 통과 항목의 개선 제안은 건수에 넣지 않는다.
4. **목적 안내**: 입력 형태나 문서 유형에 따라 덧붙일 안내가 있을 때만 `ℹ️`로 시작하는 한 줄을 적는다(예: docx나 변환본은 이미지/형식 항목을 발행본에서 재확인, 본문에 이미지가 있으면 이미지 속 민감 정보와 인증 정보는 직접 확인하라는 안내). 점검 성격(외부 공개 전 자가 점검, 우수성은 보지 않음) 설명은 1번 판정 블록에 이미 적었으므로 여기서 반복하지 않는다. 덧붙일 안내가 없으면 이 블록을 생략한다.
5. **점검표**: 1부(구조와 틀), 2부(표현과 세부)로 나누어 `# / 항목 / 판정` 3열 표로 18개 항목을 번호순 나열한다. 1부와 2부는 표를 나누어 적는다. 판정은 이모지와 라벨을 함께 적는다(✅ 통과, 🔴 P0 필수 수정, 🟡 P1 권장 수정, 🔵 P2 선택 수정, ➖ 확인 불가). 통과 항목도 모두 적는다. 입력 형태상 점검할 수 없는 항목은 통과로 적지 말고 ➖ 확인 불가로 표시한다(예: 이미지 원본이 없는 본문 입력의 15번 저작권, 서식이 사라진 docx 입력의 11번 코드 표현 형식). 12번은 입력 형태와 상관없이 링크 형식과 문서 안 참조로 판정한다. 한 항목 안에서 위치마다 등급이 다르면 점검표 판정과 건수는 가장 높은 등급 하나로 적는다.
6. **보완 항목**: 걸린 항목을 P0, P1, P2 순으로 적는다. 각 항목은 `### 🔴 P0 - 14. 출처 표기`처럼 이모지, 등급, 항목 번호와 이름을 헤딩으로 단다.
7. **통과 항목**: 통과한 항목 번호를 한 문단으로 묶어, 무엇을 확인해 통과로 보았는지 적는다. 통과 항목에 개선 제안이 있으면 이 문단에 함께 적는다.
8. **푸터**: 이탤릭 한 줄로 도구 이름과 최소 품질만 본다는 안내를 적는다.

### 등급 이모지

🔴 P0 필수 수정, 🟡 P1 권장 수정, 🔵 P2 선택 수정, ✅ 통과, ➖ 확인 불가. P0는 외부 공개 전 반드시 고쳐야 하는 항목, P1은 독자의 이해를 방해해 수정을 권장하는 항목, P2는 이해에는 문제가 없으나 품질 향상을 위해 고려할 항목, 통과는 최소 기준을 충족한 항목이다. ➖ 확인 불가는 입력 형태상 점검할 수 없어 판정을 보류한 항목으로, 발행본에서 재확인한다. 확인 불가는 통과 수에 넣지 않고, P0가 아니므로 통과를 막지도 않는다.

### 보완 항목 작성 규칙

- 헤딩 다음 줄에 그 항목이 글에서 무엇을 하는지 규칙 한 문장을 먼저 적는다. 능동으로 쓰되 "작성자는" 같은 주어는 붙이지 않는다(예: "약어는 처음 나올 때 풀이를 적습니다.", "같은 표현은 한 번만 씁니다.", "외부에서 가져온 자료, 통계, 이미지에는 출처를 표기합니다."). 점검 도구를 주어로 한 "짚습니다", "봅니다"나 피동("쓰였습니다")은 쓰지 않는다.
- 규칙을 적은 뒤 줄을 띄우고, 무엇이 어디서 걸리는지 완전한 문장으로 서술한다. 서술은 능동으로 쓴다(예: "도입부 3번째 단락에서 '잊혀진'이라고 썼습니다."). 위치는 파일 입력이면 소제목이나 섹션으로, 본문 입력이면 소제목 또는 "몇 번째 단락"으로 표기한다.
- 한 항목에서 여러 위치가 걸리면 가장 높은 등급으로 헤딩 라벨을 달고, 위치마다 한 줄씩 적는다. 여러 위치가 같은 원칙에 걸리더라도 줄여 묶지 않는다.
- 정답이 정해진 항목(용어 약어 풀이, 용어 일관성, 번역 투, 비문, 겹말, 맞춤법 및 외래어 표기, 출처 표기)은 인용 블록으로 `**수정 예)**`를 덧붙인다. 출처 표기는 출처 누락 시 수정 예에 출처 표기 방식(도서/웹 문서/AI 이미지)을 함께 적는다. 대상 독자, 구조처럼 정답이 여럿인 항목은 무엇이 걸리는지만 서술하고, 표현을 대신 고쳐 주는 코칭은 하지 않는다.
